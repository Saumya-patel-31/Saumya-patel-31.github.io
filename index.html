(04)— Process

The loop behind everything I ship.

Four steps I run on every build — a weekend hackathon or a production app. Here's each one, with the receipts.

  1. 01
    Define

    One sentence. One number.

    Before any schema or screen, I write the problem as a single sentence and pick the metric that would prove it's solved. If I can't, I'm not ready to build — and neither is the scope.

    ProofCampusly — “a network only verified students can join” → .edu OTP auth + campus-scoped Row-Level Security.

  2. 02
    Prototype

    Riskiest slice first. Real data, zero polish.

    I build the scariest part end-to-end before anything pretty. A rough prototype surfaces the hard problems in hours; a polished mock hides them for weeks.

    ProofCarryover — blank repo to a prize-winning demo in one weekend at hackUMBC 2026.

  3. 03
    Harden

    The work users never notice.

    Auth, access rules, empty / loading / error states, tests, and a fallback for when an API goes down. Boring on purpose — it's what turns a demo into something you'd trust with real users.

    ProofHeadsUp — role-based Firestore security rules across 9 collections, plus static analysis and live-database validation.

  4. 04
    Ship & listen

    Production is the real spec.

    Ship early, put it in front of real people, and let what they actually do — not what I assumed — set the next priority. The version that launches is a first draft.

    ProofHeadsUp — TestFlight beta for user-acceptance testing on iOS, Android & web. Campusly — live with 100+ users.
